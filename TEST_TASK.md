# Тестовое задание: интерактивное распределение секций и составление расписания

## Контекст

Необходимо реализовать прототип интерфейса для сотрудника университета, который ежедневно распределяет учебные секции по недельному расписанию.

Основной сценарий работы должен строиться вокруг **Drag & Drop**. Backend разрабатывать не требуется: исходные данные предоставлены в виде mock JSON.

Цель задания — оценить не количество реализованных экранов, а качество интерфейса, работу со сложным состоянием, архитектуру frontend-кода и удобство повседневной работы с расписанием.

## Основная задача

На одном рабочем экране необходимо отобразить:

- список учебных секций;
- недельную сетку расписания;
- уже назначенные занятия;
- прогресс распределения каждой секции;
- понятную информацию о конфликтах и невозможных действиях.

Пользователь должен иметь возможность распределять занятия преимущественно через Drag & Drop.

## Обязательные сценарии

### 1. Секция → расписание

Пользователь перетаскивает секцию из списка на свободный слот недельного расписания.

После Drop необходимо создать занятие. Если для секции преподаватель не назначен либо требуется выбрать аудиторию, допускается открыть компактный editor/popover/modal.

### 2. Занятие → другой слот

Существующее занятие можно перетащить на другой день и/или время.

Интерфейс должен визуально показывать потенциальное новое положение занятия до завершения Drop.

### 3. Невалидный Drop

Во время перетаскивания пользователь должен понимать, допустим ли выбранный слот.

Минимально необходимо проверять:

- преподаватель уже занят в этом слоте;
- аудитория уже занята в этом слоте;
- вместимость аудитории меньше количества студентов;
- преподаватель недоступен согласно `teacherBlockedSlots`;
- секция уже имеет занятие в этом же слоте.

Невалидный Drop должен быть запрещён, а причина конфликта — понятна пользователю.

### 4. Возврат в нераспределённые

Существующее занятие можно удалить из расписания через Drag & Drop обратно в область нераспределённых секций либо в отдельную Drop Zone удаления.

После этого счётчик распределённых занятий секции должен обновиться.

## Недельное расписание

Используйте рабочую неделю Пн–Пт и временные слоты из mock-данных.

Пример структуры экрана:

```text
┌───────────────────────┬───────────────────────────────────────────────┐
│ Секции                │ Расписание                                  │
│                       │ ПН      ВТ      СР      ЧТ      ПТ           │
│ CS101-01              │ 08:30   [ ]     [ ]     [ ]     [ ]          │
│ 2 / 3 занятия         │ 10:00   [ ]     [ ]     [ ]     [ ]          │
│                       │ 11:30   [ ]     [ ]     [ ]     [ ]          │
│ DB202-01              │ ...                                           │
│ 1 / 2 занятия         │                                               │
└───────────────────────┴───────────────────────────────────────────────┘
```

Точный UI не задаётся специально. Нам интересно увидеть собственное решение кандидата.

## Работа со списком секций

Для каждой секции желательно показывать как минимум:

- код секции;
- название предмета;
- количество студентов;
- преподавателя, если он назначен;
- требуемое количество занятий в неделю;
- количество уже распределённых занятий.

Рекомендуется визуально различать:

- не распределено;
- распределено частично;
- распределено полностью.

Например: `2 / 3`, progress indicator или другой понятный вариант.

## Работа с занятием

Карточка занятия в расписании должна позволять понять как минимум:

- секцию / предмет;
- преподавателя;
- аудиторию.

Должна быть возможность изменить преподавателя и/или аудиторию после создания занятия.

## UX-требование

Представьте, что пользователь ежедневно работает с несколькими сотнями секций.

Интерфейс должен минимизировать лишние действия и позволять быстро понимать:

- что ещё не распределено;
- где есть свободные слоты;
- почему конкретный Drop невозможен;
- где находится нужная секция;
- сколько занятий осталось распределить.

Поиск, фильтры и дополнительные средства навигации кандидат выбирает самостоятельно.

## Mock-данные

В приложении используйте `schedule-mock-data.json`.

Backend делать не требуется. Разрешено загрузить JSON напрямую либо обернуть его в локальный mock-service с Promise/искусственной задержкой.

Состояние созданных и изменённых занятий достаточно хранить в памяти приложения. Сохранение после перезагрузки страницы не является обязательным.

## Технические требования

- TypeScript.
- Любой современный frontend framework.
- Разрешены готовые Drag & Drop библиотеки.
- Компоненты и бизнес-логику желательно разделять.
- Проверки конфликтов не должны быть жёстко зашиты непосредственно в JSX/template обработчики.
- Проект должен запускаться стандартной командой из README.
- Backend, авторизация и база данных не требуются.

## Что НЕ требуется

Не нужно:

- реализовывать сервер;
- делать авторизацию;
- делать несколько страниц приложения;
- повторять дизайн какой-либо существующей системы;
- тратить время на pixel-perfect визуал;
- реализовывать все возможные правила университетского расписания.

Главный фокус — интерактивность, Drag & Drop, UX и качество frontend-архитектуры.

## Bonus

Необязательные улучшения:

- Undo / Redo;
- фильтр по преподавателю;
- фильтр по аудитории;
- поиск секций;
- подсветка допустимых и недопустимых слотов во время Drag;
- автоматический подбор подходящей аудитории;
- keyboard-accessible альтернатива Drag & Drop;
- адаптивная работа интерфейса;
- сохранение состояния после refresh;
- mock API с loading/error состояниями;
- возможность копирования занятия;
- удобная работа с большим количеством секций.

Bonus-функции не должны ухудшать качество обязательной части.
